*Written 2026-08-15 so nobody has to reconstruct this from the code again.

## 1. One engine, three faces

Paldexia is a breeding companion whose answers must be **provable**. That
constraint dictates the whole shape: one pure-TypeScript engine, oracle-tested
against 44,851 precomputed outcomes from the game files, wrapped in three
different user interfaces.

| Target | Folder | Stack | Role |
|---|---|---|---|
| **iPhone app** (priority) | `palworld-breeding/mobile/` | Expo SDK 54, RN 0.81, TS | What the CEO actually uses |
| Website / PWA | `palworld-breeding/app/` | Vite + Preact, TS | Same features in a browser; carries the test suite |
| Reference + pipeline | `palworld-breeding/` | Python 3 stdlib | The original oracle + the data-extraction tools |

### The engine rule (non-negotiable)

`engine/` exists **twice**, once per TS target, and the shared files are
**byte-identical**. Verified 2026-08-15:

```
boosters.ts  formula.ts  helpers.ts  odds.ts  planner.ts  types.ts
```

Two files are web-only because they exist to move planning off the UI thread
in a browser: `planClient.ts`, `planner.worker.ts`. Mobile calls the planner
directly.

**Change one copy → change both → re-run the oracle.** Never let the two
drift; a forked engine means the phone and the website give different answers
about the same pair, which destroys the one thing this product sells.

## 2. Mobile code map (`mobile/src/`)

35 TypeScript files. Nothing is generated at runtime.

```
App.tsx              root; wires navigation + stores
nav/domains.ts       THE navigation registry — domains, their tabs, icons
screens/             one file per screen: Calculator, Planner, Odds,
                     Paldex, Reference, Settings, ComingSoon
ui/                  shared components: PalPicker, FilterSheet, PalDetail,
                     PalMap, MapViewer, DomainPanel, Icon, kit, celebrate,
                     palFilters (shared filter/sort LOGIC, used by both the
                     Paldex and the plan-target picker — keep them unified)
engine/              the shared engine (see above)
data/                lookup tables; *.g.ts files are GENERATED by tools/ —
                     never hand-edit icons.g.ts, regionSpots.g.ts,
                     alphaSpots.g.ts
store.ts             persistence (AsyncStorage), profiles/worlds
theme.ts             colors, spacing — no hardcoded colors in screens
```

**Navigation is CEO-final** (2026-08-15): side panel = domains
(Breeding / Map / Tools & Items / Bosses & Raids / Settings); bottom bar =
that domain's tabs with the **Paldex always in the centre slot**. The Map
domain is fullscreen with no bottom tabs (`tabs: []`). Do not restructure
without him. No emoji anywhere in app chrome — vector icons via `ui/Icon.tsx`.

## 4. How code gets from this repo onto the CEO's iPhone

This is the part that has cost the most time, so it is spelled out fully.
There are **two independent delivery paths**, and they serve different apps.

### Path A — live reload (the DEV app)

```
edit a file  →  Metro rebuilds  →  ngrok tunnel  →  Palforge DEV on the phone
```

1. CEO double-clicks `START-APP.cmd`.
2. It runs `mobile/scripts/start-dev.js`, which launches
   `npx expo start --dev-client --tunnel --clear`.
3. **Tunnel only. There is no LAN fallback, deliberately** — he tests on 5G
   away from home, and a `192.168.x.x` URL dies the moment he leaves.
4. The script polls the local manifest, extracts the tunnel host, and writes
   the deep link to the clipboard + `CURRENT-DEV-URL.txt` / `.html`.
5. He taps **Connect to PC** on the install-dev page (or the captured link).
   The app bundles and runs. Shake = refresh menu.

Requires the START-APP window to stay open. Close it and the DEV app has
nothing to load from.

### Path B — OTA update (the FAST app)

```
eas update  →  Expo's update servers  →  app fetches on next launch
```

- `PUSH-UPDATE.cmd` publishes to **both** branches, `development` and
  `preview`, because the two installed builds listen on different channels.
- **This is the ONLY way the full app ever changes.** Live coding publishes
  nothing — Metro serves the working tree to the dev client and stops there.
  Reinstalling the full app does not help either: the download is a fixed
  binary from build time. If nobody publishes, the full app rots.
  Publishing after every finished item is therefore a standing obligation —
  the ritual is in `CLAUDE.md`.
- `app.json` sets `checkAutomatically: ON_LOAD`, so the app looks for an
  update when it starts; the CEO just reopens the app.
- OTA carries **JavaScript only**. Icons, permissions, native modules and
  anything in `app.json`'s native section need a full EAS rebuild.
- `runtimeVersion` follows `appVersion` (currently `1.0.0`). **If you bump
  `version` in `app.json`, every installed build stops receiving updates**
  until it is rebuilt — the runtime versions no longer match. This is the
  classic silent "why did updates stop" failure.

### Which app is which

| | DEV | FAST |
|---|---|---|
| EAS profile | `development` | `preview` |
| Channel | `development` | `preview` |
| Build config | Debug + dev client | Release |
| Metro / shake / bundling screen | ✅ | ❌ by design |
| Needs the PC | ✅ | ❌ |
| Updates via | live reload | OTA on reopen |

### App identity — `mobile/app.config.js`

Expo reads `app.json` first and passes it to `app.config.js`, which swaps the
identity per build profile:

| Resolved for | name | bundle id | scheme | icon |
|---|---|---|---|---|
| `preview` / `production` | Palforge | `com.palandre.hatchlab` | `palforge` | `icon.png` |
| `development` **and local `expo start`** | Palforge DEV | `com.palandre.hatchlab.dev` | `palforge-dev` | `icon-dev.png` |

The DEV icon is the normal mark with an orange **DEV** band across the bottom
(full width, so iOS's corner mask never clips the lettering). Regenerate it
with `python scripts/make-dev-icon.py` after any change to `icon.png`. Icons
are native — **an OTA update can never change them**, only a rebuild can.

**Pending rename:** the `name` values become Paldexia / Paldexia DEV at the
next build (`11_RENAME_TO_PALDEXIA.md`). Bundle ids and schemes stay as they
are — renaming those makes a different app to iOS and loses his saved data.

Local `expo start` deliberately resolves to the DEV identity: the dev server
must speak the same scheme as the installed dev client or the connect link
opens nothing. **Never "tidy" the release branch of that config** — it is what
keeps the CEO's installed FAST app and its OTA updates working.

Because the scheme is now per-profile, `start-dev.js` no longer reads the
scheme from `app.json`. It takes the **resolved** scheme from the running
server's own manifest, and identifies "our" Metro by `slug` (`hatchlab`),
which is identical across profiles.

Shipped in DEV build `ccefd7d2` (2026-08-15) and verified by unpacking the
`.ipa`: `CFBundleIdentifier com.palandre.hatchlab.dev`, display name
"Palforge DEV", scheme `palforge-dev`. **The two apps now coexist on the
phone.** Re-verify the identity on every new DEV build — the check is in
`01_LINKS.md`.

## 5. Builds and deploys

- **App builds**: `npx eas-cli build --profile development|preview --platform ios`.
  `EXPO_TOKEN` is a user-level Windows env var so the CLI is pre-authenticated,
  **but creating iOS credentials needs the CEO's interactive Apple login** —
  eas-cli refuses to prompt without a real terminal, so that step is his.
- **Website**: built from `app/`, served from the `main` branch at
  `/palforge/`. There is **no CI that deploys Pages** — it only updates when
  someone pushes to `main`. `app/public/` is copied verbatim into the build,
  which is where the two install pages live.
- **CI** (`.github/workflows/ci.yml`) runs the oracle gate on every push to
  `palworld-breeding/**`. It does not deploy anything.

## 6. Quality gates — all green before "done"

```bash
cd palworld-breeding/app    && npx vitest run      # 278 tests incl. 44,851-row oracle replay
cd palworld-breeding/app    && npm run build       # stricter typecheck + PWA + sw.js
cd palworld-breeding/mobile && npx tsc --noEmit    # native typecheck
```

Plus, before claiming a UI change works: load it with your own eyes (RN-web
on port 8085), and confirm the phone bundle compiles (HTTP 200 from the
tunnel). **Kill the 8085 instance when the QA pass ends** — see
`06_TROUBLESHOOTING.md` for what leaving it running cost.

## 7. Pinned versions that bite

- **`babel-preset-expo` must stay pinned to `54.0.10` exactly.** Installing
  "latest" pulls a future-SDK preset (57.x) that ships `#private` fields and
  a broken winter-runtime order to the phone → `[runtime not ready]
  SyntaxError` / DOMException crashes. Cost an hour on 2026-08-14.
- Use `npx expo install` for Expo dependencies, never bare `npm i`.
